# Spec 02: 遗留脏数据与垃圾数据清理

## 目标

清除影响仓库观感、演示稳定性和后续维护判断的历史垃圾，让仓库重新变得可读、可控、可交付。

## 为什么必须做

当前仓库中已经能看到一些明显的历史包袱：

1. 编译或运行产物痕迹。
2. 备份目录与迁移快照目录。
3. 平台无关或无实际运行价值的遗留文件。
4. 可能误导开发判断的历史报告文件。
5. 少量乱码注释和低质量说明文本。

这些内容不一定会直接导致功能错误，但会显著降低项目的“完成度感”和答辩时的掌控感。

## 清理范围

### 一类：应优先清理的仓库垃圾

1. 不应入库的编译产物和运行缓存。
2. 无实际用途的历史 `backup`/`archive` 内容。
3. 明显重复或过期的调试报告。
4. 本地平台专属但不参与项目运行的二进制或中间文件。
5. 误提交的系统文件，如 `.DS_Store`。

### 二类：需要人工判断后清理的历史资产

1. 旧迁移脚本。
2. 只服务于过时部署路径的文档。
3. 与当前主链路无关的临时测试页面。
4. 重复实现的组件或备份文件。

### 三类：保留但归档说明的内容

1. 仍可能参考的部署经验文档。
2. 与 Worker、快照、自修复有关的故障排查材料。
3. 毕设论文撰写可能会引用的历史背景信息。

## 清理原则

1. 只删“确认无运行价值”的内容。
2. 删除前先区分“运行依赖”和“历史痕迹”。
3. 能归档说明的，不直接粗暴删除。
4. 任何可能影响主链路运行的目录都必须先验证用途。

## 建议执行顺序

1. 清理系统垃圾文件与编译产物痕迹。
2. 梳理 `backups/`、`archive/`、测试残留页面与历史脚本。
3. 检查根目录与子应用目录中的误提交文件。
4. 补齐 `.gitignore` 与目录治理规则。
5. 最后做一轮目录结构复查，确保没有新“视觉噪音”。

## 输出结果

本任务完成后，仓库应该具备以下特征：

1. 根目录更干净，目录用途更清晰。
2. 非运行必须文件数量明显下降。
3. 新人查看仓库时能快速判断主结构。
4. 不会因为历史垃圾误判系统复杂度。

## 验收标准

1. 根目录只保留对当前项目有意义的结构。
2. 误提交的系统文件和明显产物被移除。
3. 备份和历史报告经过清理或归类处理。
4. 清理后项目仍可按本地演示路径运行。
