# Spec 05: 本地演示环境与答辩展示

## 目标

将 Relax-Git 收敛为一个可在本地稳定运行、便于答辩讲解、便于截图留档的演示系统。

## 当前决策

当前阶段不再以 VPS 上线为目标，而是以“本地稳定演示”作为验收基线。

这样调整的原因是：

1. 本地演示已经足以支撑本科毕业答辩主体。
2. 上线会额外引入域名、HTTPS、容器编排等非核心风险。
3. 当前更重要的是项目主链路稳定、范围清晰、讲解顺畅。

## 本地演示定位

本阶段的定位为：

`本地运行的全栈毕业设计演示系统`

重点不是公网访问，而是：

1. 能稳定启动。
2. 能顺畅演示核心链路。
3. 能配合答辩讲清楚架构与数据流。

## 本地演示对象

1. Web 前端
2. API 服务
3. Worker 服务
4. PostgreSQL
5. Redis

## 建议运行方式

优先采用自己最熟悉、最稳定的本地方案：

1. 本地开发命令直接运行服务。
2. 保持固定端口和固定启动顺序。
3. 使用本地 `.env` 管理配置。
4. 演示前准备一套稳定测试数据。

当前推荐命令已经固定为：

1. `pnpm docker:dev`
2. `pnpm db:setup`（首次或重置后执行）
3. `pnpm dev`
4. `cd apps/worker && go run .`

## 本地演示架构说明

本地服务职责如下：

1. `web` 负责页面展示、交互和控制台入口。
2. `api` 负责业务接口、认证、社区数据和后台聚合。
3. `worker` 负责快照、队列任务和健康检查。
4. `postgres` 保存业务数据。
5. `redis` 提供缓存和队列支撑。

## 演示前必须确认的事项

1. 启动命令和顺序固定，避免现场排错。
2. 关键账号可登录，管理员账号可进入控制台。
3. 仓库导入、社区浏览、评论或通知至少一条主链路可完整演示。
4. 控制台可展示真实统计与健康状态。
5. 演示数据必须是真实本地数据，不允许依赖预置示例账号或 mock 数据。

建议附带确认以下本地地址：

1. `http://localhost:3000`
2. `http://localhost:3001/api/docs`
3. `http://localhost:3001/health`
4. `http://localhost:3002/health`
5. `http://localhost:3000/console`

## 需要完成的关键点

1. 明确本地演示环境配置项。
2. 明确 Web、API、Worker 的进程关系。
3. 明确数据库和 Redis 的本地数据准备策略。
4. 做最少一轮完整演示路径验证。
5. 补齐答辩截图、架构图和流程说明。

## 建议执行步骤

1. 清理遗留调试脚本和无用资源，保证仓库干净。
2. 固定本地运行方式，并整理一份最短启动说明。
3. 准备一份手动创建的答辩账号与真实本地数据。
4. 按“首页 / 社区 / 导入仓库 / 控制台”顺序做一轮完整彩排。
5. 记录截图与答辩讲稿中的关键页面。

## 首轮验收建议

答辩前至少保留一组本地演示证据：

1. 首页或社区首页可正常打开。
2. 登录成功后可进入用户态页面。
3. 管理员账号可进入 `/console`。
4. 控制台可看到 API、Worker、数据库、Redis 状态。
5. 本地启动步骤可以在短时间内稳定复现。

## 论文与答辩可引用内容

本任务将直接支撑以下内容：

1. 系统部署架构图
2. 运行环境说明
3. 本地运行截图
4. 演示功能验收结果
5. 系统联调与交付能力说明

## 风险提醒

1. 不要为了“看起来更完整”继续引入部署复杂度。
2. 不要为了演示效果扩展过多边缘功能。
3. 优先保证可用和可讲清楚，而不是“技术栈更炫”。
4. 不要在答辩环境中继续保留开发调试页面或一次性脚本。
5. 本地环境变量和真实本地账号仍要妥善管理，不要提交敏感信息。

## 数据约束

本地演示阶段明确约束如下：

1. 不允许在运行时保留 mock 数据。
2. 不允许保留预置示例账号。
3. 不允许保留自动登录捷径。
4. mock 数据仅允许存在于测试目录和测试场景中。

## 验收标准

1. 项目可在本地稳定运行。
2. Web、API、Worker 本地结构明确。
3. 至少有一套可复现的本地启动与演示步骤。
4. 本地环境可用于答辩展示，而不只是短暂跑通。
