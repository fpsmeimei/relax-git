# Spec 03: 毕设导向的适度瘦身

## 目标

通过“适度收缩，而不是阉割项目”，让系统更容易讲清楚、更容易演示、更容易答辩，同时保留代码社交平台应有的关系能力与技术亮点。

## 核心判断

当前项目的问题不是功能太少，而是产品叙事曾经摇摆在“协作工具、社区平台、聊天平台”之间。

如果不做收缩，答辩时会自然冒出以下问题：

1. 这个系统到底是仓库协作工具，还是开发者社交平台？
2. 社区、关系、快照、评论、AI 之间谁是核心，谁是补充？
3. 哪些社交能力是平台必需，哪些是过重扩展？

因此，本任务的目标不是“删到只剩 CRUD”，而是把主叙事收拢为一个稳定的毕设产品：

`一个以开源仓库为内容单位、以代码快照和行级评论为互动基础的开发者代码社交平台。`

## 建议保留的主链路

1. 用户认证与基础身份体系。
2. 仓库导入、仓库管理与仓库发布。
3. 社区 feed 与仓库内容发现。
4. 基础快照 / 会话快照 / 代码浏览。
5. 行级评论、回复、通知与互动反馈。
6. 好友、私聊、在线状态组成的轻量关系层。

这几块共同构成完整的毕业设计核心系统。

## 建议保留但降级的加分项

1. 专用 AI 助手：只保留仓库推荐、按方向找仓库、仓库简介三类能力。
2. 社区扩展玩法：保留基础展示，不继续做复杂生态化设计。
3. 高级统计与性能展示：保留对开发和控制台有帮助的最低可用形态。

## 建议重点收缩的方向

1. 过于分散注意力的页面与入口。
2. 与主链路重复表达的功能。
3. 演示价值低、讲解成本高的边缘功能。
4. 需要大量说明但业务收益不高的复杂交互。
5. 会把项目拖向“完整 IM 系统”的重社交能力。

## 产品叙事要求

瘦身后，项目要能够用一句话讲清：

`Relax-Git 是一个以开源仓库为内容载体、以代码快照和行级讨论为核心互动方式的开发者代码社交平台。`

如果某个模块很难自然放进这句话里，就应该考虑降级或隐藏。

但要注意：

1. 社区互动是主线，不应被误判为边缘功能。
2. 轻量好友与私聊是社交闭环的一部分，不应整体删除。
3. 群聊、聊天室、泛聊天 AI 这类高复杂度扩展才是优先考虑冻结的对象。

## 实施策略

1. 先统一产品定义，让“代码社交平台”成为唯一主语。
2. 再收导航和入口，让主路径更明确。
3. 再收页面和模块，把过重扩展后置。
4. 最后收文案和对外表述，让答辩叙事统一。

## 期望结果

1. 首页和主导航更聚焦。
2. 用户一眼能看出这是“代码社交平台”而不是杂糅平台。
3. 答辩时可以围绕一个稳定故事展开。
4. 保留足够的技术亮点，但不让老师被过重扩展带跑。

## 验收标准

1. 导航结构与页面入口明显聚焦主链路。
2. 社区、评论、好友、私聊被统一纳入主叙事，而不是零散存在。
3. 专用 AI 被明确降级为辅助能力，而不是泛聊天主系统。
4. 系统模块数量与对外叙事更加一致。
5. 演示流程能在短时间内完整走通。
